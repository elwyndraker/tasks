# Multiplayer Creator-Fee Mining Game — Development Plan

## 1. Product Goal

Build a browser-based multiplayer mining game where players explore a shared pixel-art world and collaboratively compete for rewards by mining the same resources.

Rewards are funded by creator-fee revenue generated by a Solana token.

The game should combine:

- multiplayer gameplay
- mining mechanics
- resource scarcity
- real-time competition
- creator-fee-funded rewards
- Solana wallet ownership
- limited-time events

---

# 2. Development Strategy

Development should happen feature-by-feature.

Do not build the entire project as one large implementation.

Each major gameplay feature should be treated as an independent development unit.

Recommended order:

    Foundation
        ↓
    Authentication
        ↓
    Game World
        ↓
    Player Movement
        ↓
    Multiplayer
        ↓
    Rock System
        ↓
    Mining System
        ↓
    Reward Ledger
        ↓
    Events
        ↓
    Wallet Claims
        ↓
    Creator Fee Integration
        ↓
    Production Hardening

Implement WebSocket multiplayer.

    position_x

    rock_type
    size_class
    durability

# 11. Phase 8 — Mining System

Player approaches rock.

Client sends:

    mine_request

Server validates:

    authenticated player
    rock exists
    rock active
    player distance
    mining cooldown
    player state
    rock durability

Server performs:

    durability decrement
    contribution update
    activity update
    reward ledger update

Server broadcasts:

    rock:damaged

When durability reaches zero:

    rock:depleted

---

# 12. Phase 9 — Mining Contribution Engine

Create a dedicated reward calculation module.

Input:

    RockState
    MiningContribution
    ActiveMinerState
    RewardPoolState

Output:

    PlayerRewardAllocation

The module must be deterministic.

Do not put reward calculations directly inside WebSocket handlers.

---

# 13. Phase 10 — Reward Ledger

Create an immutable-style accounting ledger.

Suggested entities:

    reward_pools
    rock_reward_allocations
    player_reward_balances
    reward_ledger_entries
    claim_records

Every balance-changing operation should create an auditable ledger record.

Never simply update:

    player.balance += reward

without an associated accounting record.

# 15. Phase 12 — Anti-Cheat

Implement:

## Rate limiting

Prevent impossible mining frequency.

## Distance validation

Player must be within valid range.

## Server-authoritative durability

Client cannot modify rock durability.

## Request replay protection

Mining requests require unique request IDs or sequence validation.

## Movement validation

Reject impossible movement.

## Session validation

Verify authenticated player identity.

## Suspicious behavior logging

Record:

- abnormal mining rate
- repeated invalid requests
- impossible movement
- request spam

---

# 16. Phase 13 — Reward Pool

Implement internal reward-pool accounting.

Required concepts:

    total_funded
    available
    allocated
    claimable
    distributed

Invariant:

    allocated + available <= funded

and:

    claimable <= allocated

The exact accounting model must be formally defined before real money is connected.

# 17. Phase 14 — Solana Integration

Only after the internal game economy works should Solana reward settlement be connected.

Components:

    Solana RPC
    wallet adapter
    treasury wallet
    transaction verification
    claim transaction builder

The blockchain integration should be isolated from the game engine.

Suggested package:

    packages/solana/

The game server should communicate with this module through a narrow interface.

# 18. Phase 15 — Creator Fee Funding

Build a creator-fee funding pipeline.

Conceptual flow:

    Creator Fee Source
          ↓
    Treasury Detection
          ↓
    Fee Verification
          ↓

          ↓
    Game Economy

The system should verify deposits rather than trusting manually entered values.

Every treasury deposit should have:

- transaction signature
- amount
- token/mint
- timestamp
- source
- confirmation state

- server-authoritative gameplay
- secure wallet authentication
- deterministic reward calculations
- auditable reward ledger
- funded reward pool
- no over-allocation
- duplicate claim protection
- multiplayer synchronization
- anti-cheat validation
- creator-fee deposit verification
- reliable Solana transactions
- database backups
- error monitoring
- production logging
- documented economy rules

# 33. Primary Development Principle

Build the game loop first.

The fundamental loop is:

    Explore
       ↓
    Find Rock
       ↓
    Mine
       ↓
    Other Players Join
       ↓
    Compete / Cooperate
       ↓
    Rock Breaks
       ↓
    Reward Allocated
       ↓
    Find Next Rock

If this loop is not fun without real money, adding real-money rewards will not solve the underlying gameplay problem.

The economy should enhance the game rather than replace the game.
