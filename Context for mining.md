# A1 Context — Multiplayer Creator-Fee Mining Game

## 1. Project Overview

The project is a browser-based multiplayer mining game inspired by the core concept of Bitcoin mining.

The game takes the idea of:

- multiple miners working toward the same block,
- mining difficulty,
- shared mining targets,
- block completion,
- mining rewards,

and converts it into a visual multiplayer game world.

Instead of computers performing cryptographic mining, players physically mine objects such as rocks using pickaxes.

The game world contains:

- villages
- barren land
- mountains
- mining areas
- rocks
- special resource areas
- event locations
- rare/high-value mining objects

Players enter the game through a browser, connect a Solana wallet, and participate in mining.

The game's economic rewards are funded by creator-fee revenue generated by tokens launched by the game creator on Pump.fun.

The objective is to create a fun game around the concept of mining rather than creating a conventional play-to-earn system.

---

# 2. Core Game Concept

The main gameplay loop is:

1. Creator launches a token on Solana.
2. The token generates creator-fee revenue through trading.
3. A portion of creator-fee revenue is allocated to the game's mining reward pool.
4. The game periodically creates mineable rocks/resources.
5. Players enter the game world.
6. Players discover rocks.
7. Multiple players can mine the same rock simultaneously.
8. Every successful mining action contributes toward breaking the rock.
9. The rock has:
   - durability
   - total reward value
   - mining state
   - participating miners
10. The reward is dynamically distributed among the miners.
11. When the rock reaches zero durability, it breaks.
12. Players receive/claim their earned reward.
13. New rocks become available.
14. Special mining events occasionally occur.

---

# 3. Important Economic Principle

The game should not promise that every player receives a fixed reward regardless of the game's available funds.

The game reward pool is limited by actual creator-fee revenue.

Therefore:

    Available Reward Pool
            |
            v
    Game Treasury / Reward Pool
            |
            v
       Mineable Rocks
            |
            v
       Player Rewards

The frontend should display the current funded reward pool.

The game should never create unlimited liabilities that exceed the funded reward pool.

# 4. Rock System

Every rock is an individual mineable object.

Each rock has unique properties.

Example properties:

- rock_id
- position
- visual_type
- size
- durability
- remaining_durability
- total_reward
- remaining_reward
- active_miners
- spawn_time
- expiration_time
- status

Possible rock states:

- SPAWNING
- ACTIVE
- DEPLETED
- EXPIRED
- SETTLEMENT_PENDING
- SETTLED

---

# 5. Rock Durability

Rock durability determines how many successful mining actions are required before the rock breaks.

Example only:

A rock might have:

    total_reward = $10
    durability = 50

This does NOT mean the actual production game must use these numbers.

The game should support configurable durability and reward ranges.

For example:

Small rock:

    lower durability
    lower reward

Medium rock:

    medium durability
    medium reward

Large rock:

    high durability
    high reward

Rare rock:

    very high durability
    very high reward

Legendary rock:

    extremely high durability
    extremely high reward

The relationship between size, durability and reward should be configurable from the server.

---

# 6. Mining Actions

A player uses a pickaxe to mine.

Every valid mining action causes:

    remaining_durability -= 1

The action should only count if the server validates it.

The client must never be trusted to directly modify:

- reward balance
- durability
- player earnings
- rock state

The server is authoritative.

---

# 7. Multiple Players Mining One Rock

Multiple players can mine the same rock simultaneously.

Example:

    Rock Reward = $10
    Rock Durability = 50

If one player mines:

    $10 / 50 = $0.20 theoretical reward per mining action

If two players are actively participating, the reward allocation can be divided between them.

Conceptually:

    Base Mining Value = Rock Reward / Rock Durability

Then:

    Player Share = Base Mining Value / Active Miner Count

Example:

    Base Mining Value = $0.20

Two active miners:

    $0.20 / 2 = $0.10 each

Three active miners:

    $0.20 / 3 = approximately $0.0667 each

The actual production formula should be finalized during economy balancing.

---

# 8. Important Anti-Abuse Rule

"Active miner" must not simply mean:

    wallet connected to the rock.

A player should only count as an active miner if they are genuinely participating.

Possible definition:

A player becomes active after performing a valid mining action.

A player remains active for a short activity window.

Example:

    Mining action
        |
        v
    Active status
        |
        v
    Activity timeout
        |
        v
    Player removed from active miner list

This prevents players from joining a rock and remaining permanently entitled to a share without mining.

---

# 9. Mining Reward Accounting

Rewards should be calculated server-side.

A possible model:

    rock_reward
    rock_durability
    valid_mining_actions
    active_miners
    player_contribution

The system records player contribution.

Example:

    Rock:
        reward = 100
        durability = 500

Players:

    Alice = 100 mining actions
    Bob   = 250 mining actions
    Charlie = 150 mining actions

Total:

    500 mining actions

The final reward distribution can be based on either:

A. Equal active-miner splitting

or

B. Contribution-weighted splitting

or

C. Hybrid model

The exact production formula should be tested before launch.

---

# 10. Rock Completion

When:

    remaining_durability == 0

the rock breaks.

The server:

1. Stops additional mining.
2. Calculates final participant rewards.
3. Records the settlement.
4. Marks the rock as DEPLETED.
5. Updates player balances.
6. Makes the reward claimable or automatically distributes it depending on the chosen architecture.

The client displays a breaking animation.

    Gold Mountain

This is a temporary high-value mining event.

A large gold/resource mountain appears in a designated location.

Example event lifecycle:

        |

        |

        |
        v

Target event duration:

The Gold Mountain should feel significantly different from normal rocks.

Possible properties:

---

# 16. Reward Pool Safety

The game must never allocate more rewards than the funded pool can support.

Example:

    Reward Pool = $1,000

The system cannot create:

    $10,000

worth of active rock liabilities.

The backend should maintain:

    available_reward_balance
    allocated_reward_balance
    claimable_player_balance
    distributed_reward_balance

with accounting invariants.

---

# 17. On-Chain vs Off-Chain Architecture

Mining actions should primarily be handled off-chain.

Reason:

A player may perform many mining actions.

Putting every pickaxe action directly on Solana would create unnecessary transaction overhead.

Recommended model:

    Player
       |
       v
    Browser Game
       |
       v
    Game Server
       |
       +----> Database
       |
       +----> Reward Ledger
       |
       v
    Claim System
       |
       v
    Solana
       |
       v
    Player Wallet

The blockchain should primarily handle:

- wallet ownership
- deposits/funding
- reward claims
- treasury transactions
- optional token interactions

The game server handles:

- movement
- mining actions
- rock state
- multiplayer synchronization
- event state
- player contribution
- anti-cheat
- reward accounting

# 18. Multiplayer Synchronization

The game should support real-time multiplayer state.

Potential technology:

    WebSocket

or:

    Socket.IO

The server broadcasts:

- player movement
- mining actions
- rock damage
- rock depletion
- new rock spawn
- event start
- event end
- player joins/leaves

The client should not repeatedly poll the server for real-time game state.

---

# 19. Backend Authority

The server is authoritative.

Client requests:

    "I mined this rock."

Server validates:

    - authenticated wallet
    - player position
    - rock exists
    - rock is active
    - player is within mining range
    - mining cooldown
    - anti-bot checks
    - rock still has durability

Then:

    accept mining action

or:

    reject mining action

---

# 20. Anti-Cheat

The game will require strong server-side validation.

Potential abuse:

- automated clicking
- modified client
- fake mining requests
- impossible movement
- request replay
- simultaneous duplicate requests
- reward manipulation
- fake wallet identity
- multi-account farming
- botting

The client should never determine final rewards.

# 29. Core Product Philosophy

The game should feel like:

    "A multiplayer mining game funded by real creator-fee revenue."

It should NOT feel like:

    "A crypto dashboard with a mining animation."

The gameplay comes first.

The blockchain provides the economic infrastructure.

---

# 30. Critical Design Constraint

The game economy must always distinguish between:

    gameplay reward calculation

and:

    actual withdrawable funds

A player can accumulate an internal reward balance, but withdrawals must only be possible when the corresponding reward is actually funded and available.

The backend must maintain a verifiable accounting system.
